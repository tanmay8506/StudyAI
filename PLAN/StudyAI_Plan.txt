Summary — What Makes This Different
1. What We Are Building
A study platform for Delhi University B.Sc. students on NEP/UGCF 2022.
One input. One UPC. Everything else handled automatically.
A DU student enters their paper code and receives a complete exam-oriented study package. Notes calibrated to exactly how their specific paper is examined — topic by topic, unit by unit. Definition, concept, examples, PYQs with year tags, quick checks. Unit closes with formula sheet and 20-question problem set with full answers. Nothing irrelevant. Nothing missing.
Study this properly and top the exam. That is the only promise. It is kept through a 12-agent pipeline that verifies itself before the student ever sees the output.
This is not a general study tool. It is not an AI tutor. It is not a flashcard app. It is one thing: the most exam-calibrated study notes that have ever existed for DU B.Sc. NEP papers. Every decision in this plan serves that one purpose.
2. The Note Philosophy — Non-Negotiable
Notes are the same whether the student studies 2 weeks out or 1 day out. There is no separate revision mode, no separate crash course track. The notes are already the most efficient version of the content.
Every word earns its place. If it is not asked in DU exams it is not in the notes. If it is in the notes it will be asked.
The student studies once, studies properly, and does not need to go anywhere else. No bloat. No fluff. Adults learning for results.
The notes are not a document. They are a database of structured knowledge about one exam paper. The document the student sees is a rendered view of that database. These are two different things and keeping them separate is the most important architectural decision in the content system.
Every field in the notes is a discrete database entry. Every field is generated, verified, criticised, and patched independently. This is what makes surgical refinement possible. This is what makes the platform maintainable. This is what makes it correct.
3. Scope Definition
Framework: NEP/UGCF 2022 only. No CBCS mixing ever. Not one CBCS question appears in the notes.
Launch Faculty: All B.Sc. courses under NEP — Physical Sciences, Mathematical Sciences, Life Sciences, and all related combinations.
Semesters: I through VIII, all from day one.
PYQ Policy: Only NEP-era papers. However many years exist for that UPC — 1, 2, 3, or 4. Clearly shown to the student with year tags on every question. No CBCS mixing ever.
Language: English at launch. Hindi toggle in Phase 2. The database stores both English and Hindi content from generation day one so retrofitting is never needed when Hindi launches.
Expansion: B.Sc. proven first, then faculty by faculty.
4. The Product Name
Name: StudyAI
One-liner: Study notes built from your DU question paper.
Every design decision, every UX decision, every content decision references this positioning. The product is the notes. The promise is exam calibration. The one-liner is what appears on the landing page, in the browser tab, and in every student's head when they describe the platform to a friend.

7. The Architecture — How Everything Connects
Student (Next.js on Vercel)

         |

         | submits UPC

         ↓

FastAPI (Railway)

         |

         | checks pipeline cache (is this UPC already generating?)

         | if yes → subscribe to existing Realtime channel

         | if no → triggers new pipeline, returns pipeline_id immediately

         |

         ↓

Pipeline Orchestrator (FastAPI background task)

         |

         | Agents 1-4 run sequentially (Decoder → Researcher → DNA → Mapper)

         | Agent 4 outputs independence map

         | Independent units fire Writer agents in parallel

         | Each agent writes to Supabase as it completes

         |

         ↓

Supabase PostgreSQL

         |

         | unit status: queued → generating → verifying → complete / failed

         |

         ↓ (Supabase Realtime pushes status changes)

         |

Student sees live pipeline progress

Unit renders immediately when status flips to complete

Student reads Unit 1 while Units 3 and 4 are still generating

If a unit fails → PartialDeliveryNotice renders with retry status
Core principle: The pipeline runs in the background. The student never waits for full completion before seeing anything. First unit renders in approximately 90 seconds. Full paper ready in approximately 4 minutes.

9. The 12-Agent Pipeline — Full Detail
Agent 1 — Decoder
Model: None. Rule-based database lookup. Zero AI cost.
Receives: UPC string.
Disambiguation step — critical addition:
Before any lookup, the Decoder checks if the UPC maps to multiple programme combinations in the UPC registry. If it does, it returns a disambiguation prompt to the frontend — a single dropdown: "This paper exists in multiple programmes. Which are you enrolled in?" One tap. Then proceeds with the correct programme context.
Does: Looks up master_source_map.json and upc_registry.json. Validates UPC format. Outputs all paper metadata including documentation_tier from tier_classifier.py.
Outputs: Paper metadata JSON. Writes to papers table. Sets pipeline_status to "queued."
Fails if: UPC not found in registry. Returns: "This UPC is not in our system yet. Check your paper code or submit it for addition."
Agent 2 — Researcher
Model: Gemini 2.5 Pro.
v1 Critical Simplification — Manual PDF Input:
Gemini cannot browse the web, download files, or search exam.du.ac.in. For v1 (personal testing), all source PDFs are placed manually in the project:
Syllabus PDF → source_pdfs/{upc}/syllabus.pdf
PYQ papers → source_pdfs/{upc}/pyq_2023.pdf, source_pdfs/{upc}/pyq_2024.pdf, etc.
The pipeline reads from these local paths. No web scraping. This is sufficient for testing 1-2 papers.
PDF Type Detection — before any extraction:
pdf_detector.py identifies what Gemini is actually receiving:
Text PDF → extract directly, confidence: high
Scanned/image PDF → enhanced OCR pass, confidence: medium, flag for human review if below threshold
Combined university document → extract only the section matching the UPC paper name
Low confidence extractions set syllabus_confidence to "low" on the papers table and trigger a human review flag before pipeline continues.
Call 1 — Syllabus extraction: Full PDF in one pass. Outputs structured JSON: every unit, every subtopic, prescribed books, suggested books, hours per unit, practical components.
Call 2 — PYQ reading: Reads each PYQ PDF from the local source_pdfs/{upc}/ directory. Extracts raw question text. Attempts year extraction from each document (not just relying on filename).
Researcher Verification Pass — Groq Llama 3:
After Gemini outputs the syllabus JSON, a Groq call receives the raw PDF text and the structured JSON side by side. Mechanical checks only:
Every unit name in JSON appears in PDF?
Every subtopic in JSON appears under its correct unit in PDF?
Any units in PDF missing from JSON?
Binary flags. If any fire → Agent 2 re-runs before pipeline continues. Prevents the entire pipeline building on a corrupted syllabus.
Total calls: 1-3 Gemini (syllabus + each PYQ PDF) + 1 Groq verification.
Agent 2c — PYQ Normaliser
Model: Groq Llama 3. Runs immediately after Agent 2.
Purpose: DU question papers are not standardised in format across colleges or years. This agent normalises all PYQ papers into a consistent JSON format before Paper DNA runs. Without this, Paper DNA quality varies wildly depending on which college's paper format it sees.
Receives: All raw PYQ papers from Agent 2.
Does: Standardises every PYQ paper into:
json
{

  "year": 2024,

  "year_confirmed": true,

  "questions": [

    {

      "number": 1,

      "total_marks": 6,

      "parts": [

        {

          "part": "a",

          "marks": 2,

          "instruction_word": "define",

          "topic_hint": "Cauchy sequence"

        },

        {

          "part": "b",

          "marks": 4,

          "instruction_word": "prove",

          "topic_hint": "Cauchy sequence boundedness"

        }

      ]

    }

  ]

}
Reconciles sub-parts. Attributes marks correctly. Standardises instruction words (what is / define / state → all standardised to their canonical form). Flags any question where year cannot be confirmed from the document text.
Output: Normalised PYQ collection. This is what all downstream agents use — not the raw papers.
Agent 3 — Paper DNA Generator
Model: Gemini 2.0 Flash (2 calls). No Groq call needed.
Paper DNA is four distinct analyses producing four structured JSON objects. Not one monolithic report.
Analysis 1 — Structural DNA (No AI call — computed from normalised PYQ data)
Total marks, section breakdown, choice structure, time per section, MCQ component, paper format ratios. This is a deterministic aggregation of the normalised PYQ collection from Agent 2C — not an AI inference. Code computes it directly from the JSON.
Analysis 2 — Topic DNA (Gemini 2.0 Flash)
Per topic across all normalised PYQ years: appearances, marks value each time, question type each time, which unit it appeared in, marks migration pattern (increasing/stable/decreasing), never-asked flag, recency weight (1.5x for most recent year's questions).
Recency weighting: Questions appearing for the first time in the most recent available year receive 1.5x weight in priority scoring. A question appearing in 2024 for the first time is more likely to appear in 2025 than a question that appeared in 2022 but not since. Recent appearances are stronger signals, not weaker ones.
Analysis 3 — Language DNA (Gemini 2.0 Flash, combined with Topic DNA call)
Every instruction word extracted and counted. Frequency of each. Which instruction words appear with which topics. Exact examiner vocabulary per topic — specific phrases DU uses repeatedly. This feeds the Examiner's Note field directly.
Analysis 4 — Combination DNA (Gemini 2.0 Flash, separate call)
Which topics DU never asks alone. Which topics always carry a diagram requirement. Which topics always carry a numerical component even when phrased theoretically. Which sub-topics DU combines into one question across years. These combination patterns are as important as individual topic patterns.
Output: Four structured JSON objects written to papers.paper_dna.
Agent 4 — Mental Model Mapper
Model: Gemini 2.0 Flash (Tier 1). One call.
Receives: Syllabus JSON + Paper DNA (Topic DNA specifically — so the Mapper knows which topics are high priority and can optimise the sequence accordingly).
Cycle Detection — critical addition:
Mathematical and scientific subjects frequently have circular conceptual dependencies. Before outputting the sequence, cycle_detector.py runs on the dependency graph. If a cycle is detected (Topic A requires Topic B, Topic B requires Topic C, Topic C requires Topic A), it resolves by identifying the most foundational topic in the cycle (typically the definition-level topic), marking it as the entry point, and adding a note: "Mutual dependency exists — introduce this topic first with intuitive definition, return for formal rigour after adjacent topics are covered."
Concept Bridges — critical addition:
For every prerequisite link, the output is not just "Topic B requires Topic A." It outputs:
Which specific concept from the prerequisite is needed
Why it is needed
The one-line bridge sentence connecting them
This bridge sentence is the opening of the dependent topic in the Writer. The student never hits a concept cold.
Outputs: Dependency graph JSON + optimised sequence + independence map (which units and topics can be processed in parallel) + concept bridge sentences + split_generation flags for complex topics.
Agent 5 — Writer
Model: Gemini 2.0 Flash.
One call per topic — not per unit.
Attention degradation across a long unit-level call means Topic 6 gets worse treatment than Topic 1. Every topic gets its own focused call. Uniform quality across all topics.
Each Writer call receives:
This topic's syllabus content only
This topic's Paper DNA (Topic DNA, Language DNA, Combination DNA entries only)
The concept bridge from Agent 4
The two adjacent topics for context only
Note style category for this paper
Diagram-heavy flag
Primary textbook for this UPC
Whether split_generation is flagged for this topic
Mandatory scratchpad reasoning before any field is written:
What is this topic really about in one sentence?
How does DU actually test this based on Paper DNA?
What does a full-marks student know that a passing student doesn't?
What is the single most important thing to communicate?
This costs 150-200 extra tokens per topic. The quality improvement is significant.
Output format: Strict JSON matching the topics schema exactly. Not prose. Not markdown. Every field a discrete value from the first moment of generation.
Depth calibration by marks:
2-mark questions only → definition + one example only
3-4 mark questions → definition + concept + one example
6-mark questions → full treatment: definition, concept, analogy, two examples, answer writing technique, common mistakes, answer writing technique
Never-asked → single line: "On syllabus. Has not appeared in any NEP DU exam. Definition only."
LaTeX requirement:
All mathematical expressions output in LaTeX syntax using $ delimiters for inline and $$ for display. The Writer prompt enforces this explicitly. Example: "A sequence ${x_n}$ is Cauchy if for every $\varepsilon > 0$ there exists $N \in \mathbb{N}$ such that $|x_n - x_m| < \varepsilon$ for all $n, m > N$."
Prompt caching:
The system prompt is split into invariant (cached) and variant (not cached) portions. The invariant portion — output schema, constitutional constraints, LaTeX requirements, depth calibration rules, scratchpad requirement, word economy rule — is kept static across all topic calls. Gemini 2.0 Flash handles all per-topic calls efficiently at zero cost via Google AI Studio.
Split generation for complex topics:
Topics flagged split_generation = true by Agent 4 (estimated output exceeding 6,000 tokens) are generated in two calls: Content call (all text fields) and Examples call (worked examples and PYQs only). Orchestrator combines. Each call stays within comfortable token limits.
Parallelisation:
Topics within a unit with no inter-topic dependencies fire simultaneously. A six-topic unit where topics 1, 3, and 5 are independent fires three Writer calls in parallel.
Unit-Level Generation (after all topics in a unit complete):
After all topics in a unit pass through the Writer, two additional calls fire per unit (both use Gemini 2.0 Flash — Tier 2):
Problem Set generation — Produces the 10-question problem set (reduced from 20 for v1). Sources questions from PYQs first. Remaining questions are generated by the AI from the topic content (the pipeline does not have textbook content — only the textbook name). Full answers required.
Unit Summary generation — Produces conceptual_summary, unit_closer.exam_ready_checklist, and the appropriate sheet (formula_sheet / diagram_reference_sheet / key_terms_sheet based on paper_type).
These write to the problem_sets, formula_sheets, and units tables respectively.
Agent 6 — Semantic Coverage Checker
Model: Groq Llama 3 (Tier 3). Mechanical, fast, free.
Two-directional coverage check (v1 — string matching, no embeddings):
Direction 1 — Syllabus to Notes: All syllabus topics covered in notes? Checks every syllabus subtopic has a corresponding topic in the generated notes. Flags any syllabus topic not adequately addressed.
Direction 2 — Notes to Syllabus: All notes content traceable to syllabus? Flags content not traceable to any syllabus topic. Gemini 2.0 Flash has broad knowledge and may write correct information not part of this specific paper. Irrelevant content is not neutral — it costs the student study time on content that will not be examined.
Contextual bridge exception — critical addition:
Content in the prerequisite_bridge field and analogy field is explicitly excluded from the Direction 2 check. These fields are expected to contain material connecting to topics outside the immediate syllabus. Only definition, core_concept, and examples fields are checked for irrelevant content. The Coverage Checker is aware of the schema structure — not just checking prose against prose.
Output: Coverage gaps (add these) + irrelevant content flags (remove these). Both fed to Agent 8.
Agent 7 — Verifier
Model: Groq Mixtral + Groq Llama 3 (numerical) / Gemini 2.0 Flash (proof and derivation).
Two modes — paper type determines which fires per topic:
Numerical Mode (Groq):
For calculation-based topics. Groq Mixtral solves each worked example independently. Compares to notes answer. Standard verification for Medium and Low Priority topics. Dual verification (Mixtral + Llama 3) for High Priority numerical topics — both must agree. If they disagree with each other → manual review flag.
Proof and Derivation Mode (Gemini 2.0 Flash) — critical addition:
For proof-heavy papers (Real Analysis, Abstract Algebra, Pure Mathematics, theoretical Physics). The Numerical Verifier cannot verify proofs. A Gemini call checks:
Does each logical step follow from the previous step?
Are all assumed results either axioms, previously proven theorems, or syllabus-stated results?
Is the conclusion valid from the final step?
Any step that appears to be a logical jump without justification?
Fires for High Priority proof topics only. Cost justified — a wrong proof in the notes is the worst possible content failure.
Life Sciences diagram check:
For diagram-heavy papers, checks that all labeled parts in the diagram block match the primary prescribed textbook. Wrong label names lose marks in DU even with correct placement.
Agent 8 — Critic
Model: Gemini 2.0 Flash.
Receives: One topic at a time. One topic only.
Has access to: The DU-specific constitutional document (critic_constitution.txt). Field-by-field specification. Not general quality rubric. DU-specific compliance.
Constitutional document — field-by-field specification:
Definition: Under 40 words? DU-acceptable for 2-mark question? No undefined terms a first-year student would not know?
Core Concept: Uses an analogy? Analogy verifiably correct? Connects to prerequisite via concept bridge?
Examples (numerical): Units shown on every intermediate step? Answer boxed? Common error callout present?
Examples (theory): Matches how DU uses this concept in PYQs, not how textbook uses it?
Examiner's Note: References specific PYQ pattern by year? Contains exact instruction word from Language DNA? Specifies what full marks includes that passing doesn't?
Examiner's Note (proof topics — additional check): States exact hypothesis required before proof begins? Names most common logical error for this specific proof? Specifies expected proof technique? States exact concluding statement required?
Answer Writing Technique: Present for all 6-mark topics? Specifies structure by sentence not just paragraph? Includes word count target?
Quick Checks: All three answerable from notes content? At least one requires application not recall? None too easy?
Rapid Revision: Contains minimum viable exam knowledge? Student who reads only this knows what they need for basic marks?
LaTeX: All mathematical expressions in LaTeX syntax? No raw unicode math symbols?
Output: Structured diff JSON only. No prose. Field-level corrections.
json
{

  "topic_id": "uuid",

  "corrections": [

    {

      "field": "definition",

      "issue": "Contains undefined term 'eigenspace' without explanation",

      "correction": "Remove 'eigenspace' or define it inline"

    },

    {

      "field": "examples[0].steps[2].units_shown",

      "issue": "Units missing from intermediate step 2",

      "correction": "Add kg·m/s² after the force value"

    }

  ]

}
Agent 9 — Rewriter
Model: Gemini 2.0 Flash.
Receives: Only the flagged fields from Agent 8's diff JSON. Not the full topic. Not the full unit.
Does: Makes targeted replacements. Updates database at field level. Does not touch unflagged content.
Micro-validation after rewriting — critical addition:
After patching, a lightweight Groq call re-checks only the patched fields against the constitutional document. Did the fix introduce a new violation? If yes → one more Rewriter pass. Maximum 2 micro-validation cycles per field. If it fails twice → manual review flag rather than infinite loop.
This prevents the refinement loop from introducing new errors while fixing old ones.
Agent 10 — Final Examiner
Model: Gemini 2.5 Flash (Tier 3 — free). Coverage checking is mechanical comparison.
Receives: All normalised PYQs + only Rapid Revision blocks and topic summaries.
Check 1 — PYQ Coverage:
Every question that has appeared in DU exams addressed in notes? Checks at summary level first. If gap found → requests full topic content for that specific topic only.
Check 2 — Marks Coverage (critical addition):
Total marks available across all PYQ papers. Total marks the notes adequately prepare the student for. Ratio must be above 90%. A topic can be present but treated too lightly. A 6-mark question requires: definition, full concept, worked example, answer writing technique, and at least one PYQ with key steps. Any missing → marks-incomplete flag.
Recency weighting applied:
Most recent year's questions receive 1.5x weight in coverage analysis. Ensures the most likely future exam content is covered to the highest standard.
Output: Uncovered PYQ list + marks-incomplete topic list. Both fed to Agent 11.
Agent 11 — Patcher
Model: Gemini 2.5 Flash (Tier 3 — free). Structured additions to existing content.
Receives: Uncovered PYQ list + marks-incomplete topic list + relevant topic sections only.
Does: Adds what is missing. For uncovered PYQs — adds question to topic's PYQ array with correct year tag and key steps. For marks-incomplete topics — adds missing fields.
Post-patch regeneration — critical addition:
After patching a topic, a targeted Gemini 2.0 Flash micro-call re-generates only three fields for that topic: quick_checks, rapid_revision, and connects_to. These summary fields must reflect all content including patches.
The unit's conceptual_summary is also re-generated if any topic in that unit was patched. Summary must reflect complete final state of the unit.
One additional Gemini call per patched topic. One per patched unit. Prevents internal inconsistency after patching.
Agent 12 — Consistency Checker
Model: Groq Llama 3. Mechanical. Fast. Cheap.
DU-specific checklist — not generic:
Notation consistency: Same quantity uses different notation in same type of problem — flagged. Notation that varies by problem dimensionality or context is not flagged (scalar vs vector form in Physics is valid variation). The checker uses the accepted notation variations list from the paper type specification.
Definition consistency: Term defined one way in Topic 2, different implication in Topic 7 — flagged.
Unit consistency in numericals: Mixed SI and CGS across topics without explicit conversion — flagged. Most common source of wrong answers in Physics and Chemistry.
PYQ year consistency: Same question tagged as two different years — flagged immediately.
Priority tag consistency: Topic tagged High Priority but PYQ coverage lower than a Medium Priority topic — flagged for review.
Never-asked tag consistency: Topic tagged never-asked but appears in normalised PYQ collection — flagged immediately. Cannot have both.
LaTeX consistency: Mathematical expressions using raw unicode symbols instead of LaTeX — flagged for reformatting.
Output: Minor violations auto-patched by rule. Major violations returned to Agent 8 for that specific topic only.

10. The Parallel Processing Architecture
The problem with sequential processing:
Units generated sequentially means the student waits 5-7 minutes seeing nothing. Trust collapses before reading a word.
Dependency-aware parallel processing:
Agent 4 outputs the independence map. Units without inter-unit dependencies fire their Writer agents simultaneously. Within units, topics without inter-topic dependencies fire simultaneously.
Timeline (realistic for v1):
T+0s      UPC submitted

T+60-90s  Agents 1-4 complete (Gemini PDF reading is ~15-30s per PDF)

T+3-4min  First unit complete (all topics written + unit summary)

T+4-5min  Second unit complete

T+5-6min  Third unit complete

T+6-7min  Fourth unit complete

T+8-10min Verification + Critic + Consistency complete for all units
Unit status drives frontend:
Each unit has a status field. Frontend subscribes via Supabase Realtime. Unit renders the moment status flips to complete. Student starts reading at T+90s.
Graceful partial delivery — critical addition:
When a unit fails after retries are exhausted:
Failed unit renders with: "This unit encountered an error and is being retried automatically."
All successfully completed units remain fully accessible.
If retry succeeds → unit renders, student notified.
If retry fails 3 times → "This unit could not be generated. Flagged for manual review. All other units are available."
The student never loses completed content. Never sees a frozen screen with no explanation. Partial delivery is always better than total silence.

Orchestrator State Tracking
If the pipeline crashes mid-run and you restart, the orchestrator must know where to resume.
Strategy: Before calling each agent, the orchestrator checks what data already exists in the database:
Papers row exists with syllabus data? → Skip Agent 1-2.
paper_dna field populated? → Skip Agent 3.
Topics have dependency data? → Skip Agent 4.
Topic content fields populated? → Skip Agent 5 for that topic.
And so on for each agent.
This is simpler than maintaining a separate pipeline_runs table — the database IS the state. If a field has data, that agent's work is done. If it's null, it needs to run.
Manual override: orchestrator.py --force-rerun-from=5 forces re-execution from Agent 5 onwards, clearing downstream data.
Cost Kill Switch
cost_tracker.py counts every API call and estimates token spend:
python
MAX_API_CALLS_PER_RUN = 120      # hard limit

MAX_ESTIMATED_COST_PER_RUN = 8.00  # USD, hard limit

WARN_COST_THRESHOLD = 5.00         # USD, logs warning
If either limit is hit, the pipeline halts immediately, saves all completed work to the database, and logs the reason. This prevents infinite retry loops from burning your API budget.
Every API call logs: agent_name, model, input_tokens, output_tokens, latency_ms, success, retry_count, estimated_cost.

13. The Frontend — Complete Component Architecture
Every database field maps to a specific React component with specific behaviour. Notes rendered as components, not as a document.
PipelineProgressView
Live view of all 12 agents with status icons: queued (grey), running (animated pulse), complete (green), failed (red). Unit cards appear below as each completes — student starts reading Unit 1 while others generate. First thing seen after UPC submission. Builds trust before reading a word.
RapidRevisionCard
Always visible when topic is collapsed. Three lines. Tap to expand. Most-seen component in the product. Exam-morning use case is primary design constraint. Scanning all cards across a unit takes 2 minutes.
DefinitionBlock
Clean, bordered, distinct background. Slightly larger font. Student's eye lands here first on topic open. KaTeX renders all LaTeX expressions.
CoreConceptBlock
Plain background. Analogy italicised and visually separated — different type of content, different visual treatment.
ExampleBlock (Numerical)
Each step on its own numbered line. Final answer in box component. Verified badge top right — small, always present. Dual-verified examples have distinct badge. Common error in yellow callout at bottom. KaTeX throughout.
ExampleBlock (Theory/Biological)
Slightly indented. Connection to PYQ pattern shown below as a small note.
DiagramBlock
SVG renders inline. Label list directly below on mobile, beside on desktop. Draw instructions in distinct callout. Source citation in small text. Screenshot button — generates PNG via html2canvas, white background, high resolution, saved to camera roll. Works offline after saving. Not a system screenshot.
ExaminersNoteBlock
Most visually distinct component in the product. Different background colour. PYQ year references as inline tags. The student should feel they are getting insider information. Because they are.
CommonMistakesBlock
Subtly red-tinted. Each mistake numbered. Marks impact as badge beside each.
AnswerWritingTechniqueBlock
Renders only when applicable is true. Numbered steps. Marks distribution inline. Word count target shown.
PYQBlock
Visually distinct from generated content. Year tag prominent — ✓ for confirmed, ~ for unconfirmed. Marks badge. Question text in different font weight — source material not generated. Key steps as clean numbered list. Source attribution shown.
QuickChecksBlock
Three questions. Input field below each. No answer anywhere in the interface. "Check against your notes" prompt — not a reveal button. Forced re-reading is the mechanism.
ConnectsToBlock
Small. Bottom of every topic. Arrow icon, topic name, reason. Tappable — navigates directly to that topic.
FormulaSheet / DiagramReferenceSheet / KeyTermsSheet
Full-width, high contrast. Screenshot mode generates PNG via html2canvas. Sheet fills screen. Saved to camera roll.
UnitProgressBar
Persistent at unit level. Topics completed / total. PYQs attempted / total. Orientation, not gamification.
Last4HoursToggle
Single tap at paper level. Collapses everything except RapidRevisionCards, PYQBlocks, and relevant sheet. Sheet pinned to top. Same content, different rendering filter.

Pipeline continues. Modified Paper DNA uses syllabus weighting only. Notes generate with honest banner and embedded submission prompt.
Layer 2 — Student Submission System

Camera opens directly

UPC pre-filled, year selected from dropdown
Submit

Gemini attempts to extract the year from the paper itself — not just trusting the student's tag. If Gemini extracts a year matching the tag → year_confirmed = true. If mismatch → flag showing both: "Tagged as 2024. Document suggests 2023." If cannot extract → year shown as unconfirmed in notes.
Three-dimension quality verification (Groq):
Scan readability
Completeness

All three pass → automatic pipeline entry. Any fail → manual review queue with specific reason.
Reward:
Pre-committed at submission. Early access to submitted paper's notes or cross-paper credit for a different paper, selected at submission time.

Student-submitted questions tagged: "Student submitted — ~[Year]" in notes. Origin always visible.
16. The Error Reporting Loop
Every field has a FieldFlagButton. Student flags in 10 seconds.
Processing: Groq first pass checks if flagged content contradicts prescribed textbook or PYQ source. Contradiction confirmed → auto-queued for Agent 9. Unconfirmed → manual review.
Rate limiting: Maximum 10 flags per session per paper. Systematic flagging (5+ in same topic within 60s) auto-marked low confidence.
Closure: "Under review" on field after submission. "Updated — thank you" after resolution.
Trust signal: The platform publicly acknowledges notes can be wrong and has a system for fixing them. Honesty builds more trust than claiming perfection.
17. The Syllabus Change Detection System
Weekly detection: Lightweight Gemini call per cached paper. Compares content hash to syllabus_hash. Change detected → paper flagged for regeneration.
Student-facing diff notification:
Every student who accessed the paper in the last 30 days sees:
"DU updated this syllabus on [date]. Your notes are being regenerated. What changed:
Topics added: [list]
Topics removed: [list]
Hours changed: [details]"
Existing notes remain accessible during regeneration. Trust-building not trust-destroying.
18. The SVG Diagram Library
The problem with programmatic SVG generation:
AI-generated SVG code that is syntactically valid but spatially wrong for complex biological structures. Inner membrane outside outer membrane. Cristae as rectangles not folds. DU examiners award marks for correct structural representation. A spatially wrong diagram teaches the student the wrong structure — worse than no diagram.
The solution — pre-built verified SVG library:
For every diagram that appears in DU Life Sciences PYQs, a clean accurate SVG is built manually once. Stored in diagrams/life_sciences/. Indexed in diagrams/index.json mapping diagram names to file paths.
The pipeline looks up the correct SVG by diagram name. Never generates complex biological SVGs from scratch.
The svg_source field in the topic schema records "library" or "generated" so it is always clear which diagrams are verified pre-built vs programmatically created.
Programmatic SVG generation is permitted only for:
Simple geometric structures, basic chemical diagrams, linear process flow diagrams — structures where spatial relationships can be reliably encoded as code. Anything involving biological 3D structure with internal compartments → library only.
Library build process:
During cold start phase — identify every diagram that appears in DU Life Sciences PYQs across all available years. Build those first. Remaining diagrams built on demand when a paper is first generated. Each SVG verified against the primary prescribed textbook before being committed to the library.
Token implication:
Because the Writer retrieves svg_file_path from the library rather than generating SVG code, the SVG token problem (15,000-line SVG output consuming the context window) is eliminated entirely.
19. KaTeX — Mathematical Notation Rendering
Why this is non-negotiable:
Without KaTeX, every mathematical expression in Physics, Chemistry, Mathematics, and Statistics papers renders as broken unicode symbols in the browser. This is not a polish issue. It is a day-one blocking issue on the first mathematical paper tested.
What KaTeX does:
Renders LaTeX syntax into clean, accurate mathematical notation in the browser. Fast. Accurate. Industry standard.
Frontend integration:
KaTeX installed in Next.js frontend. lib/katex.ts provides render helpers. Every component that renders note content passes field text through the KaTeX render helper before display. Inline math delimited by $...$. Display math delimited by $$...$$.
Writer requirement:
The Writer agent system prompt explicitly requires all mathematical expressions to be output in LaTeX syntax. No raw unicode math. Examples of required output:
Greek letters: \varepsilon, \lambda, \omega not ε, λ, ω
Sets: \mathbb{R}, \mathbb{N}, \mathbb{Q} not ℝ, ℕ, ℚ
Fractions: \frac{dy}{dx} not dy/dx
Integrals: \int_0^1 f(x)\,dx
Vectors: \mathbf{F} = m\mathbf{a} or \vec{F} = m\vec{a} — consistent per paper notation convention
Consistency Checker includes LaTeX check:
Any field containing raw unicode mathematical symbols instead of LaTeX syntax is flagged for reformatting by Agent 12.
Formula sheet PNG generation:
Formula sheets use html2canvas to generate PNGs for student download. KaTeX renders correctly in html2canvas. PNG output is clean, high resolution, shareable on any platform.
20. The Documentation Tier Classification System
The core insight: Not all DU papers are equally documented online. The pipeline produces different quality output depending on how much source material exists. The student must know this before studying.
Tier classification is determined by the Decoder using tier_classifier.py:
Tier 1 — Fully Calibrated
3+ NEP PYQ years available
Clean text PDF syllabus (high confidence extraction)
Primary textbook widely available
Display: "Fully calibrated — based on [X] NEP question papers. All content exam-verified."
Papers: Mathematics Semester I-II, Physics Semester I-II, Chemistry Semester I-II, Computer Science Semester I-II.
Tier 2 — Partially Calibrated
1-2 NEP PYQ years available
Syllabus extracted with medium confidence
Textbook available
Display: "Partially calibrated — based on [X] NEP question paper(s). Some content estimated from syllabus. Priority tags are reliable. Depth estimates may vary."
Papers: Most subjects with 2023-2024 papers available. The majority of the platform at launch.
Tier 3 — Syllabus-Based
0 NEP PYQ years publicly available
Syllabus available
CBCS papers may exist as weak signal
Display: "Syllabus-based — no NEP question papers publicly available for this paper. Content estimated from syllabus and pre-NEP patterns where available. Treat priority tags as indicative, not definitive. Submit your question paper to improve these notes."
Papers: Geology, Food Technology, Instrumentation, Polymer Science, niche combinations.
Tier 4 — Insufficient Data
No NEP PYQs
Syllabus extraction failed or low confidence
No reliable source material
Display: "Insufficient data — we cannot generate reliable notes for this paper yet. If you have a question paper or syllabus for this UPC, please submit it. Notes will be generated once sufficient source material exists."
Pipeline halts for Tier 4 papers. No notes generated. No false confidence.
Depth Signal Hierarchy
For topics with no PYQ data, depth is estimated using this hierarchy in order:
NEP PYQ data — ground truth. If present, always used.
CBCS PYQ data for similar topic — used as estimate with label: "Estimated from pre-NEP papers — treat as indicative."
Syllabus hours allocation — more hours = more depth. Used as estimate with label: "Syllabus-based estimate — no exam data available."
Never-asked tag reserved only for topics where CBCS and NEP both show zero appearances AND syllabus hours allocation is less than 2 hours. Everything else gets minimum medium treatment with appropriate uncertainty labeling.
21. The Cold Start — 50 Seed Papers
Selection methodology — three factors simultaneously:
Factor 1 — Search frequency (Telegram groups, Reddit r/DelhiUniversity, Quora, WhatsApp groups)
Factor 2 — Supply gap (how little quality material currently exists online for this paper)
Factor 3 — Programme popularity (how many DU students need this paper)
Weighting toward Semester I and II: Every student needs these. Highest volume. Highest impact.
Subject distribution:
Mathematical Sciences (Maths + Physics, Maths + Statistics, Maths + CS) — Semesters I and II.
Physical Sciences (Physics + Maths, Physics + Chemistry, Physics + Electronics) — Semesters I and II.
Life Sciences (Botany, Zoology, Biochemistry) — Semesters I and II. High supply gap.
Chemistry all combinations — Semesters I and II.
Computer Science — Semesters I and II.
Niche combinations — disproportionately represented due to high motivation and high supply gap.
Defined spot-check protocol:
For each of the 50 seed papers, the spot-check requires a checker who has actually studied that subject. Not anyone — someone who knows the content. The checker:
Runs through the Quality Benchmark checklist (Section 24) for every item.
For every PYQ in the notes — verifies question text is exact, year tag is correct (if confirmed), key steps would receive full marks.
For every worked example — solves it independently before reading the notes solution. Flags any discrepancy.
For every diagram (Life Sciences) — verifies labels against the primary prescribed textbook.
Minimum time: 2-3 hours per 4-unit paper. Done once. The quality of these 50 papers determines whether the platform is trusted by the first students who use it.

25. The Prompt Specifications
Specifications for every AI agent. Not the final prompts — the constraints, output schemas, and failure modes each prompt must handle. The actual prompts are tuned during Stage 1 testing. These specifications define what correct looks like.
Writer Prompt — Invariant Section (Cached)
Must enforce:
Output only valid JSON matching topic_schema.json exactly. No prose. No markdown. No preamble.
All mathematical expressions in LaTeX syntax with $ delimiters. No exceptions.
Every sentence must either define, explain, demonstrate, or warn. No sentence that does none of these four.
Depth calibration: 2-mark topics → definition + one example only. 6-mark topics → full treatment. Never-asked → one line only.
Scratchpad reasoning before any field: 4-question internal pass not in output.
Definition field: under 40 words, no undefined terms, DU-acceptable for 2-mark question.
Analogy field: must connect specifically to the prerequisite bridge provided.
Example steps: units on every intermediate value for numerical examples.
Common error: specific to DU exams, not generic advice.
Rapid Revision: written as if student reads only this before the exam.
Quick Checks: no answers. At least one requires application not recall.
Must not:
Write about the topic as it appears in a textbook. Write about how DU examines it.
Include content not traceable to the syllabus, Paper DNA, or prerequisite bridge.
Use hedging language ("it is important to note," "this concept plays a crucial role").
Generate SVG code for complex biological structures.
Failure modes to handle:
Syllabus content too vague to write a specific definition → write the most precise definition possible and flag the field with low_confidence: true.
No PYQ data for this topic → depth defaults to syllabus hours weighting. Mark rapid_revision.examiner_pattern as "No NEP exam data available."
Topic has circular dependency with prerequisite → use the concept bridge provided, do not attempt to re-derive the dependency.
Writer Prompt — Variant Section (Per Topic, Not Cached)
Contains: topic syllabus content, this topic's four DNA analyses, concept bridge sentence, two adjacent topics, note style category, diagram heavy flag, primary textbook name, split_generation flag, UPC.
Critic Prompt
Must enforce:
Output only valid JSON matching diff_schema.json. No prose feedback.
Field-level corrections only. Not topic-level observations.
Every correction must name the exact field, the specific issue, and the specific correction.
Check every field against the DU-specific constitutional document, not general quality standards.
For proof topics: check Examiner's Note against proof-specific constitutional requirements.
LaTeX check: flag any field containing raw unicode math.
Must not:
Suggest stylistic changes not related to DU exam compliance.
Flag content in prerequisite_bridge or analogy fields as irrelevant.
Produce more than 10 corrections per topic (if more than 10 issues exist, prioritise by marks impact).
Researcher Prompt
Must enforce:
Output only valid JSON matching the syllabus extraction schema.
Every unit name extracted verbatim from the syllabus document.
Prescribed books extracted with full title, author, edition where available.
Hours per unit extracted exactly as stated.
If content is ambiguous → output the ambiguous content and flag it, do not guess.
Must not:
Add topics not present in the source document.
Merge units that are listed separately.
Infer syllabus content from general subject knowledge.
Paper DNA Prompt (Topic and Language Analysis)
Must enforce:
Every topic appearance recorded with year, marks, question type, and instruction word.
Instruction words standardised to canonical forms.
Recency weight of 1.5 applied to most recent available year's questions.
Examiner vocabulary extracted as exact phrases, not paraphrased.
Combination patterns identified only when appearing in 2+ years.
Must not:
Infer patterns from single-year appearances as definitive.
Conflate topics that have similar names but are listed separately in the syllabus.
Mental Model Mapper Prompt
Must enforce:
Cycle detection must run before outputting sequence. Cycles resolved with entry point designation.
Concept bridge: one specific sentence per prerequisite link, not just topic name.
Independence map: explicit list of which topics have no dependencies on incomplete topics.
split_generation flag: set for any topic estimated to require more than 6,000 output tokens.
Final Examiner Prompt
Must enforce:
Check PYQ coverage at summary level first.
Request full topic content only for topics where gap is found.
Apply 1.5x recency weight to most recent year's questions in coverage analysis.
Marks coverage check: every 6-mark topic must have all required fields present.
Output: two separate lists — uncovered_pyqs and marks_incomplete_topics.
Proof Verifier Prompt (Agent 7, Proof Mode)
Must enforce:
Check every logical step in the proof.
Verify every assumed result is either an axiom, previously proven theorem, or syllabus-stated result.
Flag any logical jump without justification.
Output: verified (boolean) + specific flagged steps with issue descriptions.
Must not:
Suggest alternative proof approaches if the current approach is logically valid.
Flag steps as wrong based on notational preference.
26. The Failure Handling Specification
Defined response for every pipeline breakpoint. Failure paths designed in, not bolted on.
Agent 1 — Decoder Failures
UPC not found in registry:
Return clear error to frontend: "This UPC is not in our system yet." No pipeline triggered. Offer: "Submit this UPC for addition."
UPC maps to multiple programmes (disambiguation):
Return disambiguation prompt to frontend. Pipeline pauses until student selects programme. Timeout after 10 minutes with no selection — pipeline abandoned, student notified.
Agent 2 — Researcher Failures
Syllabus URL returns 404:
Retry once after 30 seconds. If still failing → mark syllabus_url as broken in database, send alert for manual URL update. Pipeline continues with partial syllabus if any cached version exists. If no cached version → halt pipeline, set status to "failed", student notified: "Could not fetch syllabus for this paper. Our team has been notified and will resolve this."
Scanned PDF — OCR confidence below threshold:
Set syllabus_confidence to "low." Set documentation_tier to 3 regardless of PYQ count. Flag for human review before pipeline continues. Do not auto-proceed on low confidence syllabus.
Researcher verification pass fails:
Agent 2 re-runs. Maximum 2 re-runs. If fails both times → human review flag, pipeline halts. Student notified: "Syllabus extraction encountered issues. Being reviewed manually."
Zero PYQs found:
Not a failure. Layer 1 fallback activates. Pipeline continues with syllabus-based notes. Documentation tier set accordingly.
Agent 3 — Paper DNA Failures
Normalised PYQ JSON malformed:
PYQ normaliser re-runs that specific paper. Maximum 2 retries per paper. If still malformed → that paper excluded from DNA analysis, flagged in paper_dna with exclusion_reason.
Paper DNA output fails schema validation:
Agent 3 re-runs. Maximum 2 retries. If still failing → pipeline continues without Paper DNA for this paper, documentation tier set to 3, student sees lower confidence tier badge.
Agent 4 — Mental Model Mapper Failures
Cycle detected and unresolvable:
Flag the cycle in the dependency graph. Proceed with the most foundational topic as entry point. Notes will have a warning on the cyclically-dependent topics: "This topic has a mutual dependency with [Topic X]. Study both before sitting exams."
Output fails schema validation:
Agent 4 re-runs. Maximum 2 retries. If still failing → default to syllabus order as the topic sequence, no parallel processing for this paper.
Agent 5 — Writer Failures
Output JSON fails schema validation:
Writer re-runs for that specific topic. Maximum 3 retries with incrementally more explicit schema constraints in the prompt. If still failing after 3 → topic rendered with: "This topic encountered a generation error and is being regenerated." Unit status does not flip to complete until the topic is resolved.
Output exceeds token limit (unflagged split_generation topic):
Orchestrator catches the truncated output. Immediately triggers split_generation mode for this topic — Content call + Examples call. No retry count consumed. This is a routing adjustment, not a failure.
LaTeX syntax errors in output:
latex_formatter.py attempts auto-correction of common LaTeX errors before saving to database. If auto-correction fails → field saved with raw content and flagged for Critic's LaTeX check.
Agent 6 — Coverage Checker Failures
Groq API unavailable:
Coverage check skipped for this run. Topic proceeds to Agent 8 (Critic) without coverage data. Critic's constitutional check partially compensates. Coverage check added to queue for retry.
Agent 7 — Verifier Failures
Groq API unavailable:
Verified badge not assigned. Example saved with verified: false. Student sees no badge rather than false badge. Verifier queued for retry.
Dual verification disagreement (both models give different answers):
Field flagged for manual review. Manual_review: true set on that example. Student sees: "This example is pending expert review" rather than a verified badge.
Proof verification flags an issue:
Issue details passed to Agent 8 diff JSON. Critic incorporates into corrections. Proof not marked verified until re-verification passes after Rewriter.
Agent 8 — Critic Failures
Output JSON fails diff_schema:
Critic re-runs for that topic. Maximum 2 retries. If still failing → topic proceeds to Agent 9 without Critic corrections. Logged as quality gap.
More than 10 corrections in diff:
Critic outputs only the 10 highest marks-impact corrections. Remaining issues logged but not passed to Rewriter in this cycle. May be caught by subsequent cycles or Agent 12.
Agent 9 — Rewriter Failures
Rewriter output fails schema for patched fields:
That specific field retains its pre-rewrite value. Flagged for manual review. Other corrections in the same diff batch are applied normally.
Micro-validation fails twice:
Field sent to manual review queue. Pre-rewrite value retained. Logged with both versions for human decision.
Agent 10 — Final Examiner Failures
Output fails schema:
Final Examiner re-runs. Maximum 2 retries. If still failing → paper proceeds to Agent 11 with empty uncovered lists. Quality gap logged. Critic cycle flags this as a risk in paper metadata.
Agent 11 — Patcher Failures
Patch output fails schema:
Patch not applied. Missing content logged. Paper proceeds with gap noted in paper metadata. Student does not see an error — they see the unpatched notes with whatever the Critic cycle produced.
Post-patch regeneration fails:
quick_checks, rapid_revision, and conceptual_summary retain pre-patch values. Flagged for manual refresh.
Agent 12 — Consistency Checker Failures
Groq unavailable:
Consistency check skipped. Paper proceeds. Logged as quality gap.
Consistency violations found:
Minor violations (LaTeX formatting, notation standardisation) → auto-patched by rule-based code, no AI call needed. Major violations (definition inconsistencies, PYQ year duplications) → returned to Agent 8 for those specific topics only.
Pipeline-Level Failures
Mid-pipeline crash (any agent):
Units that completed before the crash retain their data. pipeline_status set to "partial." Student sees completed units immediately via Realtime. Failed unit renders PartialDeliveryNotice. Orchestrator attempts to resume from the failed agent for the failed unit. Maximum 3 resume attempts. After 3 → unit flagged for manual regeneration.
Complete pipeline failure:
pipeline_status set to "failed." Student notified: "Pipeline failed for this paper. Our team has been notified. Retry?" One-tap retry triggers fresh pipeline run.
Supabase Realtime disconnect during generation:
On reconnect, frontend polls database for current unit statuses immediately. Renders any units that completed during disconnect. Does not rely solely on missed Realtime events. Realtime is the fast path. Database poll on reconnect is the reliable fallback.

31. Summary — What Makes This Different
Every other DU study resource is written about the subject. This is written about the exam.
The difference is everything.
A textbook explains Eigenvalues because they are important in linear algebra.
These notes explain Eigenvalues because DU has asked "find the eigenvalues and corresponding eigenvectors of the matrix A" as a 6-mark question in both 2023 and 2024, always using the word "find" not "derive", always combined with Diagonalisation in the same question, and students consistently lose marks by not stating the characteristic equation explicitly before solving — a pattern the Examiner's Note identifies directly.
That is what exam calibration means. That is what this platform does. That is what no other resource does.
The 12-agent pipeline exists to produce that calibration reliably, verifiably, for every NEP B.Sc. paper at Delhi University. The parallel processing architecture means the student starts reading in 90 seconds. The diff-based refinement loop means every correction is surgical and token-efficient. The trust layer means every single claim is sourced and verifiable. The tier classification system means the student always knows exactly how much to trust what they are reading.
The notes are not a document. They are a database. The database is what gets built, verified, criticised, patched, and maintained. The document is what the student reads. These are two different things. Keeping them separate is what makes everything else possible.
End of plan. Version 4.0. Every decision made. Every component defined. Every failure mode addressed. Every pre-build step specified. Ready to build.
